### (a) Reframe Stage 3 — "more expressive" → "typed lifted syntax for cross-instance reuse"

**Brief says (`<a>` §1.1).** Stage 3 should NOT be framed as "make the grammar more expressive". It should be framed as: *replace object-indexed ground syntax with typed lifted syntax, so the same symbolic policy schema applies across different $D$.* Stage 1's $\lvert N\rvert = 3^K$ explosion and Stage 2's $\lvert L_=(G_2)\rvert = (2K)^{2K}$ blowup are coverage problems; lifting collapses them by sharing structure across objects of the same type. This is the *generalised planning* motivation — compact solutions valid for many instances, not one.

**Current docs say.**
- [design_lifted_grammar.md:5](design_lifted_grammar.md) — "The Stage 3 policy class is a **bounded lifted decision list** generated by a typed CFG."
- [design_lifted_grammar.md:40](design_lifted_grammar.md) — "This is a **typed CFG**, not a right-linear grammar."
- [README3.md:35](README3.md) — "$G_3$ takes the *strong* version on the first four axes ..." — describes axis position rather than the structural-compression motivation.

**Edit.** In [design_lifted_grammar.md:5](design_lifted_grammar.md), open with the *purpose* before the *class*: "Stage 3 replaces object-indexed ground syntax (Stage 1's $P_k, M_k$) with typed lifted syntax — bound variables of declared types — so the same symbolic policy applies across instance sizes. The result happens to be a typed CFG; what matters is that it shares structure across objects." ### (b) Add Chomsky-class clarification — typed CFG ≠ context-sensitive

**Brief says (`<a>` §1.6).** Typed variables do not move you up the Chomsky hierarchy. The CFG generates abstract syntax; the type system is a separate semantic layer that rejects ill-formed trees. Better terms: *typed DSL grammar*, *typed CFG with semantic well-formedness constraints*, *syntax-guided policy synthesis*, *lifted relational policy language* — not "context-sensitive grammar".

**Current docs say.** No file claims context-sensitivity, but no file proactively heads off the misconception. [design_lifted_grammar.md:40](design_lifted_grammar.md) calls $G_3$ a "typed CFG, not a right-linear grammar" without saying *why typed* still keeps it CFG-class.

### (c) Formalise notation — types, predicates, bindings

**Brief says (`<a>` §1.2–1.5).** Make four notational pieces explicit:
1. Type set $T = \{\textit{room}, \textit{key}, \dots\}$ (Doors).
2. Per-type object sets $O_\tau$, e.g. $O_{\textit{room}} = \{r_0, \dots, r_K\}$, $O_{\textit{key}} = \{k_0, \dots, k_{K-1}\}$.
3. Ground atom $p(o_1, \dots, o_n)$ vs lifted literal $p(x_1\!:\!\tau_1, \dots, x_n\!:\!\tau_n)$, with the variable annotation meaning "any object of that type".
4. Typed binding (substitution) $\theta : V \to O$ with the type-respecting condition $\theta(x_i) \in O_{\textit{type}(x_i)}$. Apply to a literal: $p(x, y)\theta = p(\theta(x), \theta(y))$.

The brief's payoff: at $D=3$, $\textit{key\_for}(k\!:\!\textit{key}, r\!:\!\textit{room})$ has $2 \times 3 = 6$ candidate bindings, not $5^2 = 25$ untyped pairs — a concrete demonstration of why typing compresses search.

**Current docs say.** [design_domain_adapter.md:13–19](design_domain_adapter.md) introduces $\mathcal T, \mathcal P, \mathcal P_{\mathrm{static}}, \mathcal A$ but stops short of $T = \{\dots\}$ enumerated, $O_\tau$ partition, and the ground-vs-lifted pair. [design_lifted_grammar.md:21](design_lifted_grammar.md) mentions "first type-respecting binding $\theta$" without defining $\theta$.

**Edit.** Add a *Notation* subsection to [design_domain_adapter.md](design_domain_adapter.md) immediately after the 4-declaration block (after line 19), enumerating items 1–4 above with the Doors instance as the running example, and the "$6$ vs $25$ bindings" payoff sentence. ### (e) Add Doors $D=3$ worked execution trace

**Brief says (`<a>` §3, §3.1).** A concrete trace makes typed binding tangible. At $D=3$ ($K=2$):

- $S_0 = \{\textit{at\_agent}(r_0), \textit{key\_available}(k_0), \textit{locked}(r_1), \textit{locked}(r_2)\}$.
- Static facts: $\textit{key\_for}(k_0, r_1), \textit{key\_for}(k_1, r_2), \textit{next}(r_0, r_1), \textit{next}(r_1, r_2)$.
- Goal: $G = \{\textit{at\_agent}(r_2)\}$.
- Three reactive lifted rules:
  - $\rho_1$: if $\textit{key\_available}(k) \wedge \textit{key\_for}(k, r) \wedge \textit{locked}(r)$ then $\textit{pick}(k)$.
  - $\rho_2$: if $\textit{has\_key}(k) \wedge \textit{key\_for}(k, r) \wedge \textit{locked}(r)$ then $\textit{move\_to}(r)$.
  - $\rho_3$: if $\textit{at\_agent}(g) \wedge \textit{goal\_room}(g)$ then $\textit{finish}$.
- At $S_0$: $\rho_1$ fires with $\theta_0(k) = k_0, \theta_0(r) = r_1$ → emits $\textit{pick}(k_0)$.
- At $S_1$: $\rho_2$ fires with $\theta_1(k) = k_0, \theta_1(r) = r_1$ → emits $\textit{move\_to}(r_1)$.
- Continues for $k_1, r_2$, then $\rho_3$ terminates.

### (f) Reactive vs program-compiler distinction

**Brief says (`<a>` §3.1 vs §3.2).** Two distinct policy targets, conflated in the current docs:
- **Reactive lifted decision-list:** $\pi(S, G) \to a$. Policy re-applied at every state. Closest to PG3. May not need `ForEach`.
- **Program-compiler:** $\Pi(O, I, G) \to [\textit{macro sequence}]$. Generates a whole sequence at once (closer to Stage 1/2's `UnmaskedSurfaceDerivationGame`). Here `ForEach(\tau, \textit{body})` *is* natural — e.g. the template $\textit{ForEach}(r\!:\!\textit{room}, \textit{locked\_path\_order})$ expands on the $D=3$ instance to $P_0, M_0, P_1, M_1, G$.

The choice matters because `ForEach` reads as essential in program-compiler mode but as one option among several in reactive mode.

**Current docs say.** [design_lifted_grammar.md:68–77](design_lifted_grammar.md) describes decision-list semantics (clearly reactive). [design_lifted_grammar.md:99–105](design_lifted_grammar.md) introduces `ForEach` as a grammar feature without flagging that it most naturally lives in the program-compiler regime. No file currently states which target Stage 3 commits to.

**Edit.** Add a short subsection — proposed location [design_lifted_grammar.md](design_lifted_grammar.md) immediately before the "Doors-specific extension: `ForEach`" header at line 99 — explicitly stating: "Stage 3 targets the **reactive** form $\pi(S,G) \to a$, re-applied at every state. The alternative **program-compiler** form $\Pi(O, I, G) \to [\textit{macro sequence}]$ — natural successor to Stage 1/2's `UnmaskedSurfaceDerivationGame` — is where `ForEach` is most natural; we keep it on the table but do not commit to it." Update [README3.md §"Where Stage 3 sits"](README3.md) (around line 35) with a one-sentence pointer to this distinction.

**Files touched:** [design_lifted_grammar.md:98 (new subsection)](design_lifted_grammar.md) · [README3.md:35](README3.md) · optional one-line mirror in [connection_to_pg3.md §"Why lift?"](connection_to_pg3.md).

### (h) SyGuS / syntax-guided synthesis framing

**Brief says (`<a>` §1.6).** Stage 3 is closely related to syntax-guided synthesis (SyGuS): the grammar defines the syntactic search space, the environment defines the semantic objective, and a search algorithm — here AlphaZero — picks expressions that satisfy the objective. Anchoring to SyGuS prevents the misreading "Stage 3 = exotic new grammar class" and locates it in established literature.

**Current docs say.** No file mentions SyGuS or syntax-guided synthesis. The appendix [appendix/sygus_background.md](../appendix/sygus_background.md) exists but is not referenced from `stage3/`.

PG3's representation slots in as the SyGuS grammar; PG3's GBFS scorer is replaced by environment reward (see §'Why replacing scorer matters')."
