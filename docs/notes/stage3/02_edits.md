## 1. Review of content `<a>`

`<a>` is a one-shot redirection brief with a single thesis:

> Stage 3 should be a Doors-only diagnostic program before claiming general PDDL transfer. The next testable question is: **can a typed lifted grammar recover the useful compression of the Stage 1 masks without hard-coding object-indexed Door policies?**

Seven concrete shifts follow from this. Listed in priority order:

1. **Doors-only narrative.** Drop Ferry / Gripper / Blocksworld as Stage 3 targets; they become future work after the Doors diagnostic completes. The cross-domain reuse experiment (currently Exp 3) is deferred.
2. **Add the `next(room, room)` predicate.** The current Doors vocabulary lacks a *local frontier abstraction*; without it, a flat lifted rule cannot express "the locked room adjacent to where I am" without `ForEach`. `<a>` argues `next` may be sufficient, making `ForEach` unnecessary.
3. **Three grammar variants A/B/C.** Replace the single grammar enumeration with a structured ablation:
   - **A:** no `next`, no `ForEach` — tests whether the grammar is too weak.
   - **B:** add `next`, flat decision list — tests whether local frontier abstraction suffices.
   - **C:** no `next`, with `ForEach` — tests control-flow alternative.
4. **Object-renaming test (mandatory mask-leakage diagnostic).** Randomly permute room/key names while preserving `next` and `key_for`. A truly relational policy still solves; one relying on lexicographic object ordering fails. This prevents Stage 3 from accidentally reintroducing Stage 1's hidden mask through binding tie-break.
5. **Three sub-stages with independent goals.**
   - **Stage 3.1 — Doors relational semantics & binding audit.** No grammar search; only verify that a manually-written lifted policy executes correctly under the typed binding engine.
   - **Stage 3.2 — Typed-grammar exact enumeration.** No neural learning; enumerate the three variants A/B/C at small bounds; report solver counts, behavior classes, renaming-robust solvers.
   - **Stage 3.3 — MCTS / AlphaZero over the lifted grammar.** Only after enumeration confirms the language; train on $D \in \{3,4\}$, evaluate on $D \in \{3,4,5,8,10,20\}$.
6. **Three distinct outputs of the system.** Make explicit:
   - `TypedPolicyGrammar` — generated by the grammar generator from the adapter; the *search space*.
   - `LiftedPolicy` AST — the learned symbolic policy; the *paper artefact*.
   - Neural weights — the prior/value heuristic; not the policy itself.
7. **MCTS-over-grammar reframe.** Stages 1–2 already established that AlphaZero is *not* "learning a grammar" — the grammar is fixed; AlphaZero searches for a policy string inside it. Stage 3 inherits this: the grammar is schema-generated from the adapter, and AlphaZero searches for a `LiftedPolicy` AST inside the grammar's language.

`<a>` also provides explicit Claude Code prompts for each of 3.1/3.2/3.3 — these belong inside the new sub-stage files as runnable specifications, not in this plan.

## 5. Issue-by-issue refinements

### (i) Doors-only narrative

**`<a>` says (§8).** The paper claim should be narrower: "In the Doors grammar-constrained AlphaZero setting, ... a typed lifted policy grammar replaces object-indexed tokens with relational action schemas and runtime object binding. In Doors, we test whether local frontier predicates and/or an explicit `ForEach` construct recover the useful compression of the masks while producing compact policies that transfer across corridor lengths."

**Edit.** In [README3.md §"Goal"](README3.md), replace the current boxed quote (line 17) — which targets "PDDL-style relational domains" generically — with `<a>` §8's narrower claim, scoped to Doors. Move the framework-portability paragraph (line 19) to a "future work" subsection in §"Open scope and forward path". In `02_doors_adapter.md`, drop the Ferry running example (current lines 33–54 of `design_domain_adapter.md`); use the Ferry vocabulary only as a brief contrast, not as the canonical worked example.

**Files touched:** [README3.md](README3.md) §"Goal", §"Open scope" · `02_doors_adapter.md` (formerly design_domain_adapter.md).

### (ii) Add the `next(room, room)` predicate

**`<a>` says (§3, §7).** "Without `next`, a flat lifted rule may know that some room is locked, but not which locked room is the current frontier." The proposed Doors vocabulary is: `at_agent`, `locked`, `has_key`, `key_available` (dynamic); `next`, `key_for` (static); actions: `pick(k)`, `unlock_move(k, r)`, `finish`.

**Edit.** In `02_doors_adapter.md`, replace the current Doors interface table (lines 58–67 of `design_domain_adapter.md`) with the `<a>` §3 vocabulary including `next`. In `01_lifted_grammar.md`, replace the Doors $D=3$ trace inserted by 01_edits.md (issue (e)) with the `<a>` §3 walk-through that uses `at_agent(u) ∧ next(u, r) ∧ locked(r) ∧ key_for(k, r) ∧ key_available(k) → pick(k)`. The trace already in place must be rewritten to include `next` — currently it relies on $\rho_2$ binding $k$ to $k_0$ via `has_key(k) ∧ key_for(k, r) ∧ locked(r)` without specifying that $r$ should be the room *adjacent* to the agent.

**Files touched:** `01_lifted_grammar.md` §"Worked example — Doors $D = 3$" · `02_doors_adapter.md` §"Concrete example — Doors adapter".

### (iii) Three grammar variants A/B/C

**`<a>` says (§7 Stage 3.2).** Three variants, each enumerated under bounds $L_{\max} \in \{1,2,3\}$, $K_s \in \{2,3,4,5\}$, $K_g \in \{0,1\}$, $V_{\max} \in \{2,3\}$:

| Variant | Predicates / control | Hypothesis |
|---|---|---|
| A | no `next`, no `ForEach` | grammar is too weak |
| B | `next` + flat decision list | local frontier abstraction is enough |
| C | no `next`, add `ForEach` | control-flow alternative suffices |

**Edit.** Encode this as the central section of the new `stage_3_2_enumeration.md`. The reported metrics per variant: raw policies, well-typed policies, canonical policies, behavior classes, solvers, solve density, shortest solver, **renaming-robust solvers** (see (iv)). The decision rule: "Stage 3 is about lifting if B alone solves; about lifting + control if only C solves; the grammar is wrong if neither solves under exact enumeration."

**Files touched:** `stage_3_2_enumeration.md` (new); `01_lifted_grammar.md` §"Candidate extension: `ForEach` for Doors" updated to point at the variant-comparison rather than committing to either path.

### (iv) Object-renaming test (mandatory)

**`<a>` says (§4).** "If the binding engine always chooses the first room by object name, then a rule like `locked(r) ∧ key_for(k, r)` might 'solve' Doors only because $r_1 < r_2 < \cdots < r_K$ in the object ordering. That would be another hidden mask. ... Randomly permute room and key names while preserving static facts such as `next` and `key_for`. A truly relational policy should still solve."

**Edit.** Add the renaming test as a mandatory diagnostic in **all three** sub-stage files:

- `stage_3_1_binding_audit.md` — manual policy must pass renaming on $D \in \{3, 4, 5, 10\}$ before any grammar work begins.
- `stage_3_2_enumeration.md` — enumeration metrics include `renaming_robust_solver_count` per variant.
- `stage_3_3_mcts_alphazero.md` — held-out evaluation always includes renamed instances.

Add a one-line note to `01_lifted_grammar.md` §"Decision-list semantics" cautioning that the lex-tie-break rule (currently rule 3) interacts with renaming: deterministic tie-break is fine for reproducibility, but *the policy's solving behaviour must be invariant to a permutation of object names*.

**Files touched:** all three new sub-stage files; `01_lifted_grammar.md` §"Decision-list semantics".

### (vi) Three outputs distinction

**`<a>` says (§5.1, §6 (iii)).** Three different objects come out of the system:

| Object | Produced by | Meaning |
|---|---|---|
| `TypedPolicyGrammar` | grammar generator from adapter | search space over lifted policies |
| `LiftedPolicy` AST | MCTS / AlphaZero search | the learned symbolic policy — the paper artefact |
| Neural weights | AlphaZero training | reusable prior / value heuristic |

**Edit.** Add this as a new subsection in `01_lifted_grammar.md` §"Overview" (right after the reframing already inserted by 01_edits.md issue (a)). Also reference it in README3.md §"Goal" so the reader knows the *output* of Stage 3 is the AST, not the grammar and not the weights.

**Files touched:** `01_lifted_grammar.md` §"Overview" · README3.md §"Goal".

### (vii) MCTS-over-grammar reframe

**`<a>` says (preamble).** "In Stage 1 and Stage 2, AlphaZero was not really 'learning a grammar.' The grammar was fixed; AlphaZero/MCTS searched for a good program / policy string inside that grammar. In Stage 3, the grammar should again be fixed or schema-generated, but now it should generate lifted relational policies rather than ground object-indexed strings."

**Edit.** Add one paragraph to README3.md §"Where Stages 1–2 left us" (after line 13) making this explicit: *AlphaZero never learned the grammar; it searched inside it. Stage 3 keeps that division and changes only what the grammar generates.* Also add a subsection to `01_lifted_grammar.md` §"Overview" titled "Schema-generated grammar, learned policy" expanding on this with the §5.2 derivation-game formalism from `<a>` (state $x_t$ = partial AST; action = production choice; terminal = complete `LiftedPolicy`; reward = rollout in Doors).

**Files touched:** README3.md §"Where Stages 1–2 left us" · `01_lifted_grammar.md` §"Overview".
